# 数据与状态文件（现状）

本文件只描述**现在**程序把哪些数据写到哪里、谁写、什么时候写、留多久。不写「应该怎样」，不含规划。

两点使用前提：

1. **行号会漂。** 本仓库工作区在并发开发，同一文件的函数位置会移动。所以每条断言都同时给出「源码位置」和「可重跑核对命令」；行号对不上时以命令输出为准。
2. **「样本」指** 本机跑出来的真实目录 `.test-twins\UserData\`（用于核对文件名与目录形状）。样本里出现过几份备份不代表程序固定生成这么多。

## 1. 数据根：三套形态与四个概念

宿主（C#）会传四个不同的路径给服务，别把它们混为一谈（`native-host/AppPaths.cs:27-41`）：

| 概念 | 参数 | 打包安装时的值 | 源码直接跑时的值 |
| --- | --- | --- | --- |
| 安装目录 | — | `AppDomain.CurrentDomain.BaseDirectory`（exe 所在目录） | `repo\source\local-service`（往上两级/四级推算） |
| `UserData` | `--app-data` | `<安装目录>\UserData` | 不适用（见下） |
| `Workspace`（= 服务里的 `root`） | `--root` | `<安装目录>\UserData`（**与 UserData 同一个目录**） | 仓库根 |
| `Data`（= 服务里的 `dataDir`） | `--data-dir` | `<安装目录>\UserData\database` | `repo\source\local-service\data` |

- `AppPaths.cs:24-26` 在 C# 侧就 `CreateDirectory(UserData)` 和 `CreateDirectory(UserData\database)`，所以这两个目录**进程还没起就已经存在**。
- 服务侧对应代码：`dataDir = resolve(options.dataDir ?? join(here, "data"))`、`databasePath = join(dataDir, "olivia-local.sqlite")`（`server.js` 的 `createOliviaService`）。打包态下 `dataDir = <安装目录>\UserData\database`，于是库落在 `<安装目录>\UserData\database\olivia-local.sqlite` —— 与样本一致。
- 由此推出（`midi/data-safety.js` 的 `backupDirOf` / `userDataDirOf`）：**备份目录 = `<UserData>\database`，UserData 根 = 备份目录的上一级**。`userDataDirOf(databasePath) = dirname(dirname(databasePath))`。
- 服务还有一条独立兜底：`appData = resolve(options.appData ?? join(process.env.APPDATA ?? dataDir, "OliviaSoul"))`（`server.js`）。打包态由 `--app-data` 覆盖成 `<UserData>`，所以走不到 `%APPDATA%\OliviaSoul` 那条分支。
- Electron 桌面壳（`desktop/`）是**另一套**：`desktop/main.js` 的 `desktopDataDir()` = 打包态 `<Electron userData>\data`、开发态 `<local-service>\data`；那一层之下**没有** `database` 子目录。`desktop/node-host.js:28-38` 解析 `--root/--data-dir/--template/--app-data`，并把 `prepareWorkspaceIncrementally()` 铺到 `root`、把 `join(appData,"settings")` 当模板设置目录。

核对：

```powershell
cd repo\source\local-service
Select-String -Path native-host\AppPaths.cs -Pattern 'UserData =|Workspace =|Data =|CreateDirectory'
Select-String -Path server.js -Pattern 'dataDir = resolve|databasePath = join\(dataDir|appData = resolve'
Select-String -Path desktop\main.js -Pattern 'function desktopDataDir'
```

## 3. SQLite：`olivia-local.sqlite`

初始化在 `server.js` 的 `initDatabase(path)`：`new DatabaseSync(path)` 之后先执行

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
```

于是每次运行都会有 `-wal` / `-shm` 两个伴随文件。

### 3.1 表

| 表 | 用途 |
| --- | --- |
| `users` | 列：`id`、`username`（唯一）、`person`、`created_at`、`last_login_at` |
| `letters` | 信件正表；索引 `letters_user_created`（`user_id, created_at DESC`） |
| `settings` | 键值表，两列：`key TEXT PRIMARY KEY`、`value TEXT NOT NULL` |
| `import_previews` | 导入预览（确认前的暂存） |
| `letter_summaries` | 每封信的摘要缓存；主键 `letter_id`，外键 `REFERENCES letters(id) ON DELETE CASCADE` |
| `memory_bulk_summaries` | 批量记忆摘要缓存 |
| `archive_projections` | 归档投影 |
| `playlist_items` | 播放列表项；索引 `playlist_items_user_created` |
| `letter_import_previews` | 信件 JSON 导入的预览暂存（`id`、`payload_json`、`added_count`、`skipped_count`、`conflict_count`、`created_at`，`server.js:604`） |
| `song_folders` | 歌单（收藏夹）正表：`id`、`user_id`、`name`、`sort_order`、`created_at`、`updated_at`；索引 `song_folders_user_order`（`server.js:651`） |

### 3.2 加列方式

**没有**「版本号 + 迁移脚本」机制，全是「先查再补」的幂等加列：先 `PRAGMA table_info(<表>)` 看列在不在，不在才 `ALTER TABLE ... ADD COLUMN`。已这样加过的列（都在 `server.js` 的 `initDatabase` 里）：`letters.source`、`letters.reply_video`、`letters.memory_order`、`letters.letter_date`、`letters.letter_time`、`letters.reply_label`、`letters.content_md5`、`letter_summaries.prompt_version`、`memory_bulk_summaries.prompt_version`、`playlist_items.duration`、`playlist_items.video_duration`、`playlist_items.video_url`、`playlist_items.performance_type`、`playlist_items.video_by_tod_view`。

核对：

```powershell
Select-String -Path server.js -Pattern 'CREATE TABLE IF NOT EXISTS|CREATE INDEX IF NOT EXISTS|PRAGMA table_info|ADD COLUMN'
```

### 3.3 开库前的顺序

`server.js` 的 `createOliviaService` 在开库前依次做三件事：

1. `prepareDatabaseBeforeOpen({databasePath, version, log})`（`midi/data-safety.js`）= 先 `applyPendingRestore()` 应用「重启后恢复」，再 `backupBeforeUpgrade()` 做升级前备份。
2. `cleanStaleSidecars(databasePath, …)` 清残留的 `-wal` / `-shm`。
3. `openDatabaseHealing(databasePath, () => initDatabase(databasePath), …)` 带自愈地打开。

升级前备份的判定（`backupBeforeUpgrade()`）：

- 版本文件不存在 → **只写版本号，不备份**（首次运行）；
- 版本号没变 → 什么都不做；
- 版本号变了但库不存在 → 只写版本号；
- 版本号变了且库存在 → 生成 `upgrade-backup-<旧>-to-<新>-<时间戳>.sqlite`；**备份失败只记日志，不拦启动**；
- 最后无论哪条分支都把当前版本写回 `last-run-version.txt`。

## 4. 保留策略汇总

只有**三类**文件会被自动清理，其余全部只增不减：

| 对象 | 规则 | 源码 |
| --- | --- | --- |
| `backup-periodic-*.sqlite` | 最多留 7 份（`DEFAULT_PERIODIC_BACKUP_KEEP = 7`），按时间清理**最早**的；正在写的那份被 `protect` 保护；删除失败只记日志 | `midi/data-safety.js` 的 `prunePeriodicBackups()` |
| `runtime.log` | 超过 4 MiB → 当前文件改名成 `runtime.previous.log`（旧的先删） | `native-host/MainForm.cs` 的 `WriteRuntimeLog()` |
| `listen-naming.log` | 超过 1 MB 自动轮转 | `midi/logs.js` 文件头注释 |
| 其它所有备份（手动 / 改时段 / 写曲名 / 社区 / 搬家 / 升级前 / 恢复前 / 导入） | **不会自动删**，只能手动清 | 同上注释：周期备份清理范围不含这些 |

周期自动备份的默认值、开关与可见性：

| 项 | 值 | 源码常量 |
| --- | --- | --- |
| 默认开关 | **开**（只有显式写 `0`/`false`/`off`/`no`，不区分大小写，才关） | `readPeriodicBackupConfig()` |
| 默认间隔 | 1 天（`DEFAULT_PERIODIC_BACKUP_DAYS = 1`），允许 1~30，越界回落默认 | 同上 |
| 检查节拍 | 30 分钟一次（`PERIODIC_BACKUP_TICK_MS = 30*60*1000`） | `midi/data-safety.js` |
| 保留份数 | 7，不可配 | `DEFAULT_PERIODIC_BACKUP_KEEP` |
| 设置键 | `periodic_backup_enabled`、`periodic_backup_interval_days`（存在 `settings` 表里） | `PERIODIC_BACKUP_ENABLED_SETTING` / `PERIODIC_BACKUP_DAYS_SETTING` |
| 状态可见性 | 进程内 Map，**重启后清空** | `periodicBackupStatus()` |

「备份列表」只截断**展示**列表（默认 60 条），不删文件：

```js
listBackups(databasePath, { limit = 60 })   // midi/data-safety.js
// → { dir, database, total, items: items.slice(0, limit), pending }
```

核对：

```powershell
Select-String -Path midi\data-safety.js -Pattern 'PERIODIC_BACKUP|DEFAULT_PERIODIC|prunePeriodicBackups|slice\(0, limit\)'
Select-String -Path native-host\MainForm.cs -Pattern '4 \* 1024 \* 1024' -Context 2,4
```

## 6. 核对方法（把这份文档验一遍）

```powershell
cd <仓库根>\repo\source\local-service

# 1) 数据根与数据库位置
Select-String -Path server.js -Pattern 'dataDir = resolve|databasePath = join\(dataDir'
# 2) 目录形状（用真实样本核对文件名）
Get-ChildItem -Recurse -Force <仓库根>\.test-twins\UserData |
  Select-Object FullName,Length
# 3) 备份种类与保留策略
Select-String -Path midi\data-safety.js -Pattern 'BACKUP_KINDS|prunePeriodicBackups|DEFAULT_PERIODIC_BACKUP_KEEP'
# 4) UserData 根下还有谁在写状态文件
Select-String -Path midi\*.js,lyrics\*.js,desktop\*.js -Pattern 'join\((userData|USER_DATA|userDataDir|userDataOf)[^)]*"[^"]+"'
# 5) settings 表结构
Select-String -Path server.js -Pattern 'CREATE TABLE IF NOT EXISTS settings' -Context 0,4
```

样本 `database\` 实测 26 个文件（4 个 `backup-manual-`、2 个 `backup-tod-`、4 个 `before-restore-`、2 个 `import-`、2 个 `upgrade-backup-`、当前库，以及 `__probe`/`__export_probe` 残留和它们的 `-wal`/`-shm`）—— 数量本身不是规范，只是旁证：文件名前缀确实按 §2.1 这张表生成。
