## 1. 一句话

「本机信件服务」接管游戏请求的方式是**改游戏自己的两个客户端文件**：

| 文件 | 里面装什么 | 打补丁的产物 |
| --- | --- | --- |
| `<版本>\resources\feapp.dat` | 界面（信件列表 / 详情 / 发送 / 歌曲编辑器入口） | 被补丁的 zip：`assets/main-*.js` 顶部加 marker，正文插入调用本机服务的代码 |
| `<版本>\resources\webplayer.dat` | 桌面播放器 | 被补丁的 zip：去掉水印、接管进度与暂停/播放命令 |

补丁由提权 PowerShell 脚本写入游戏安装目录（`repo/source/tools/patch-*.ps1`），打之前把**原版**按下文
命名规则另存一份。用户看到的「启用服务 / 停用服务 / 回退补丁（还原原版）」三个入口，前两个是历史叫法，
**后两个的还原动作走同一条链路**（见第 6 节）。

入口在界面上：`repo/source/local-service/public/index.html:289-304`
（`#mountService` :290、`#restoreClient` :291、`#rollbackPatchBox` :297、`#rollbackPatchBadge` :299、
`#rollbackPatch` :300、`#rollbackPatchHint` :302），三个按钮的点击分别接到
`app.js:1644`、`app.js:1645`、`app.js:1646` 的 `runClientMountAction("enable" | "disable" | "rollback")`。

`tools/get-feapp-status.ps1` 的 `$knownMarkers`。

### 2.4 v59 → v60 这一档是什么

- v60 是当前 feapp 补丁版本，内容是**「停止/结束后再次播放跳到列表第一首」的最小修复**：
  源码注释在 `tools/patch-feapp-local.ps1:208`（「v60：修…（根因见 `.test-twins/g82-跳列表根因.md`）」），
  测试侧说明在 `repo/source/local-service/test/api.test.js:945`（同处 :957 记录 v58/v59 补的是延迟恢复兜底）。
- `api.test.js:875-878` 明确写了：v60 只改了 `handleTogglePlay` 的「再次播放」恢复逻辑，注入结构仍是 FE v59 那一套，
  所以对外文案里「FE v59 或更高」依然成立（该行断言 `OliviaSoulPatch:mail-music-v60`）。
- 用户侧的可见后果：只有 FE 侧版本号变了，WP 仍是 `webplayer-instant-seamless-v19`（那是 v60 那一档的 WP 版本；
  现在的 WP marker 见 2.2）；
  已经打了 v59 的机器在状态判定里会落到 `updateAvailable`（见第 5 节），界面提示「客户端补丁待更新」，
  点「更新客户端补丁」走升级脚本而不是重打补丁（见第 3.3 节）。

### 2.5 v19 → v20 这一档是什么

- v20 修的是「停止本地演奏、回到默认画面时，壁纸停在挂载那一刻的时段」这个回归。回归由 v19 引入：
  `__OliviaSoulRestoreDefaultPlayback` 把默认画面当成 `{url, offset, loop}` 静态快照回放，
  跨过 16:00 / 20:00 的时段边界也不会换段，还沿用旧 offset。
- v20 的做法：`/toy/player-command` 的 GET 响应新增 `timeOfDay` 字段
  （`repo/source/local-service/server.js`，值来自 `midi/playback-clock.js` 的 `playbackTimeOfDay()`，
  与演奏视频选段共用同一个时钟），前端在轮询里缓存成 `window.__OliviaSoulCurrentTod`；
  恢复默认画面时用 `OliviaSoulCurrentTodUrl()`（`tools/webplayer-pause.js`）把快照 URL 里的
  `_(1200|1730|2000)` 改写成当前时段，并把 offset 归零。时段未知（服务不可达、响应里没有 `timeOfDay`、
  URL 不是壁纸资产、或者是 `*_Transition_*.mp4`）时**不猜段**，直接交回官方 `fe()`。
- marker 必须跟着改：`desktop/controller.js:514` 的 `keepWebplayer` 会跳过「WP 已挂载且端口一致」的重打，
  marker 不变则新代码永远不落地。
- 已知遗留：`tools/upgrade-webplayer-v6-v7.ps1` 只认 v6/v7 marker（对 v17/v18/v19 一律 throw），
  所以「WP 待更新」这条升级分支对 v17~v19 的机器本来就是坏的；FE ≥ v24 的机器走的是重打分支
  （`desktop/controller.js:511`），不会碰到它。

## 5. 挂载状态怎么判定

### 5.1 判定脚本与字段

状态只有一个来源：`tools/get-feapp-status.ps1`（127 行）与 `tools/get-webplayer-status.ps1`（64 行），
两个脚本都输出同一组 JSON 字段，由桌面壳解析：

```jsonc
{ "clientFound": true, "mounted": false, "managed": true, "updateAvailable": true, "revision": "v59", "port": 27149 }
```

调用点：`main.js:190-196`（feapp）/ `main.js:198-204`（webplayer）——
`powershell -NoProfile -ExecutionPolicy Bypass -File tools/get-*-status.ps1` + `JSON.parse`。
文件不存在时提前返回 `{clientFound:false,mounted:false,port:null}`（`get-feapp-status.ps1:9`、
`get-webplayer-status.ps1:8`）。

两个脚本都要求 zip 里 `^assets/main-[^/]+\.js$` 恰好 1 个 entry，否则抛
`expected one main-*.js, got N`（`get-feapp-status.ps1:21`、`get-webplayer-status.ps1:20`），再按 UTF-8 读全文。

### 5.2 四个判定量的定义（feapp）

`get-feapp-status.ps1`：

- `$complete`：`:31` 起 `$endpoints` 共 **21 条**路径，每条必须**恰好出现一次**形如
  `http://127.0.0.1:(\d+)/toy<endpoint>` 的地址，端口收进 `$ports`；任一条缺失/重复则 `$complete = $false`。
  唯一例外：首 marker 是 `mail-music-v11` 时只要求前 11 条（`:59` `$requiredEndpoints = $endpoints[0..10]`）。
- `$managed = $complete -and $uniquePorts.Count -eq 1 -and $activeMarker.Count -eq 1`（:120）
  —— 「确实装了本机的补丁，且补丁里的端口唯一」。
- `$mounted = $managed -and $activeMarker[0] -eq $currentMarker`（:121）—— 「装的就是当前版本」。
- `$updateAvailable = $managed -and -not $mounted`（:122）—— **有旧版补丁、可以升级**。
- `$port` 只在 `$managed` 时给出（:123-124），`$revision` 从首个命中的 marker 里抓 `v\d+`（:125-126）。
- `$knownMarkers`（:71-117）列出全部已知 marker（含 `v59`、`v11`），`$activeMarker` 取首个 `StartsWith` 命中的那个。

webplayer 侧判定条件不同（它没有端点清单，改看特征串）：`get-webplayer-status.ps1:48-52`
`$managed` = marker 命中唯一 **且** 正文里**不再含**原版水印特征串 `$watermarkShown`（:46）
**且** 含 `/toy/player-command`、`/toy/player-state`、`__OliviaSoulPlayerPoll`；
`$mounted = $managed -and $text.StartsWith($patchMarker)`（:53）。
`:55-57` 的注释写明一条硬约束：**端口提取失败不得参与 `managed`/`mounted` 判定** ——
否则已打补丁的文件会被误判成干净原版、被当成原版备份存起来，之后就再也恢复不回去。

### 5.3 桌面壳把这些字段拼成什么

Electron 壳 `getClientMountStatus()`（`main.js:206-230`）返回 `{clientSelected, clientExe, ...feapp, mounted, webplayerFound, webplayerMounted, servicePort}`，
其中 `mounted = Boolean(feapp.mounted && webplayer.mounted)`。C# 宿主 `controller.js:315` 的对应字段是
`feappMounted: Boolean(feapp.mounted || feapp.managed || feapp.updateAvailable)` ——
也就是说**旧版已知补丁在 C# 链路里算「已挂载」**（`:294` 是无客户端时的 `false` 分支）。

## 6. 还原链路：「回退补丁」与「停用服务」是同一条

```text
#rollbackPatch  (index.html:300)
  └─ app.js:1646  runClientMountAction("rollback")
#restoreClient  (index.html:291)
  └─ app.js:1645  runClientMountAction("disable")
        ├─ 二次确认：rollback → ROLLBACK_PATCH_CONFIRM (app.js:285-286)
        │             disable  → 「…与「回退补丁（还原原版）」是同一条还原链路…」(app.js:445)
        └─ 同一个调用：window.oliviaDesktop.restoreClient()      (app.js:464-465)
              └─ preload.cjs:11  ipcRenderer.invoke("client:restore")
                    └─ main.js:653  ipcMain.handle("client:restore", () => restoreClient())
                          └─ main.js:406-423  restoreClient()
                                ├─ tools/restore-feapp-original.ps1      (提权)
                                ├─ tools/restore-webplayer-original.ps1  (提权)
                                └─ return getClientMountStatus()         （复查真实状态）
```

可核对的关键点：

- 两个入口**不新写任何还原逻辑**，源码注释直说：`app.js:281-284`（「复用既有还原链路：preload.cjs 的
  restoreClient → ipc `client:restore` → main.js restoreClient()」）与 `app.js:463`（「回退补丁与「停用服务」
  走的是同一条还原链路」）。`preload.cjs:11` 只有一个 `restoreClient`；`main.js:653` 只有一个 handler。
- `restoreClient()` 只做三件事：`originalFeapp(layout)` :409、`originalWebplayer(layout)` :410、
  依次提权跑两个还原脚本（:411-421），最后 `getClientMountStatus()` :422。
  它**不会**调用 `mountClientService`（回退不会顺手重打补丁）。
- 还原脚本行为（`tools/restore-feapp-original.ps1`，45 行）：参数 `-GameRoot -Version -OriginalFile`
  `[-RestoreStudioUi] [-RestoreContainerPlugin]`（:1-7）；先 `Stop-GameProcesses $GameRoot` + `Start-Sleep 250`
  （:26-27），再把原版字节 `Copy-Item -Force` 覆盖回 `<GameRoot>\<Version>\resources\feapp.dat`（:12、:28），
  可选小部件同理（:29-34）；输出 `restored=<路径>`、`sha256=<哈希>`（:35-37）。webplayer 有同名脚本，参数一致。
- 还原后界面必须**再查一次**真实状态，不能只看这次返回的快照：`app.js:424-426`
  （`if (rollback) void refreshClientMountStatus({ preserveResult: true, expectedChange: true })`）。
  状态刷新后 `mounted=false` → `patchPresent=false` → 回退入口自动收起（:368-369）。
- 结果文案：成功 `已回退补丁：游戏文件已还原成本机备份里的原版`（:434）；
  未到位（仍报部分挂载）走 `${label}未完成：…`（:435），**不谎报成功**；
  失败 `回退补丁失败：<分类说明>`（:413-415）。
- 失败分类不新造一套：`app.js:288-299` 的 `ROLLBACK_FAILURE_HINTS` 直接用桌面层的 code
  （`BACKUP_INVALID` / `GAME_RUNNING` / `STEAM_RUNNING` / `PATH_INVALID` / `TARGET_CHANGED` /
  `RESTORE_FAILED` / `CLIENT_SERVICE_BUSY`），分类函数在 `desktop/uninstall-restore.js` 的 `classifyRestoreError`；
  没有 code 才退回脱敏后的错误首行（`app.js:376-382` `clientMountErrorMessage`）。
- 并发保护：三个按钮共用同一把写锁 `clientMountAction`（`app.js:273-279` `updateClientMountButtons`）；
  进行中收到状态快照不会解锁（:318）；120 秒超时只提示「等待超时，操作结果尚未确认；请勿重复点击」（:468-478），
  **超时不释放锁**（:474 注释）。

C# 宿主侧对应的还原入口是 `controller.js:670` `restoreClientResources({ allowUnverifiedOptionals, rollbackContext, restoreContext })`，
登记表状态转 `restored` 用 `controller.js:395`/`:461`；卸载流程里的还原见 `uninstall-restore.js:264`、`:311`。

## 9. 已知不一致 / 技术债（只登记，未修）

1. **两套备份与登记并存**（第 4 节）：Electron 壳的 `<userData>\client-backups\<md5>.{feapp,webplayer}.dat`
   与 C# 宿主的 `<UserData>\database\client-backups\resources-only\<key>\*.dat` + `client-patches.json`
   是两套互不认识的机制；「回退补丁」只在 Electron 壳里有按钮，C# 形态靠「停用服务 / 卸载还原」。
2. **登记表旧形状会让读取抛错**：`client-patch-registry.js:171` 要求 `version === 1` 且 `clients` 是数组，
   而 `readClientPatchRegistry` 只对 `ENOENT` 兜底（:198-202）；真机样本
   `.test-twins/UserData/settings/client-patches.json` 的内容是旧形状 `{"version":1,"clientRoot":"…","clientPatches":[]}`。
   据代码推断这会让读取抛 `invalid client patch registry`，**本次未在真机复现**，仅登记。
3. **marker 需要人工同步两处**：`feapp-revisions.js` 之外的 `patch-feapp-local.ps1:42` 与
   `get-feapp-status.ps1:70`/`:71-117`（该文件 :1-15 记录了这个坑的历史事故）。
4. `patch-feapp-local.ps1:720-748` 的 `New-WidgetPatchPlan` 规则是「已有原版备份就绝不覆盖」
   （:723 `$original = if ($hasBackup) { read Backup } else { $live }`，:746 用 `FileMode::CreateNew` 写）——
   这意味着**原版备份只在首次打补丁时生成**，之后不会因为再次挂载而更新；`-RefreshOriginal`（:6、:18）
   是唯一的刷新入口。
